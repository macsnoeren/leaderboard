# CLAUDE.md

Leaderboard for a manually graded team game ("Zebrawave"; detective assignments). Everything belongs to a **game** (`games`): teams, assignments, the archive and announcements. Teachers level teams up by hand; teams see their assignment on their own dashboard (no mail per level). An optional agentic AI service (Python + Ollama, `agentic-service/`) reads every team message and, depending on the team's AI mode, suggests to the teacher, replies to the team, or levels the team up itself; design and decisions in `agentic-service/README.md`. A background worker (Python, `worker-service/`) runs queued tasks: game export/import (also archives from the first `export_assignments.py`), full backups (manual and nightly) and restores, and a PDF report per game; design and decisions in `worker-service/README.md`.

## Stack
- Plain PHP + SQLite (PDO). No framework, Composer, build step, or linter. Each page carries its own inline CSS/JS on top of the shared inline `themeStyles()`/`themeScript()` from `conf/theme.php`; `marked.js` comes from a CDN at a pinned version (`MARKED_SRC`, use `markedScript()`).
- Tests: plain-PHP CLI scripts in `tests/` that exit non-zero on failure. PHP may not be installed on the host, so run them in Docker: `docker run --rm -v "$PWD":/app -w /app php:8.3-cli php tests/auth_test.php` (same for `tests/totp_test.php`, `tests/game_test.php`, `tests/ai_test.php` and `tests/worker_test.php`).
- Python tests (stdlib `unittest` + `unittest.mock`, LLM agents via a `FakeLLM`): `docker run --rm -v "$PWD":/app -w /app/agentic-service python:3.12-slim sh -c "pip install -q requests==2.32.3 && python -m unittest discover -s tests -v"`. Evals against the real models: `python3 agentic-service/evals/run.py` (and `--designer`).
- PHPMailer is a git submodule: `git submodule update --init`.
- Worker tests (stdlib `unittest`, temporary install via `tests/helpers.py`/`tests/schema.py`, `migrate.php` mocked): `docker run --rm -v "$PWD":/app -w /app/worker-service python:3.12-slim sh -c "pip install -q -r requirements.txt && python -m unittest discover -s tests -v"`.
- Python 3.10+: the agent needs only `requests`; the worker only `fpdf2` (pinned in `worker-service/requirements.txt`, for the report).
- Sanity-check PHP with `php -l <file>`.

## Layout
- `htdocs/`: web root, one PHP file per page. Pages include `../conf/*.php`.
- `conf/`: kept outside the web root on purpose. `config.php` (gitignored, copy from `config.php.example`), `database.php` (`getDB()`), `theme.php` ("Ops Room" design, see Design below; `auth.php` requires it), `mail_functions.php` (`createMailer()` + the send functions), `auth.php` (teacher auth helpers, see below), `totp.php` (pure TOTP/base32 functions), `game.php` (games, levels, teams; see below), `ai.php` (AI modes, rubrics, `get_pending` tasks, server rules, `submitEvaluation()`, escalations, assignment assistant; `game.php` requires it at the bottom).
- `bin/`: `setup.sh` (must run from inside `bin/`; also creates `storage/`) and `migrate.php` (exits 1 on failure). The old `import_assignments.py`/`export_assignments.py` are gone: use the worker (`python3 -m worker export-game|import-game|inspect|backup|restore|report`).
- `agentic-service/`: the AI agent. `main.py` (loop: heartbeat, team messages first, then design jobs) does `import config`, so `config.py` must sit beside it (sample: `agentic-service/config.py.sample`; in Docker `docker/agent-config.py` reads `AI_*` from the environment). Package `agentic/`: `api.py` (client for `api.php`), `llm.py` (Ollama `/api/chat`), `schemas.py`, `context.py` (prompt building), `prefilter.py`, `policy.py` (decision table), `pipeline.py`, `agents/` (intent, helper, assessor, validator, designer) and `prompts/*.md`. Tests in `tests/`, evals in `evals/`, `tools/check_ollama.py`.
- `worker-service/`: the background worker. `main.py` (loop: heartbeat, nightly-backup planner, claim one job, run it; hourly cleanup) and `python3 -m worker` (CLI). Package `worker/`: `config.py` (defaults; optional `config.py` beside `main.py`), `db.py` (queue: atomic claim, `restore`/`backup` run alone), `jobs.py` (`@register`, `Job`, `UserError` = message the user may see), `storage.py`, `archive.py` (safe tar.gz: allowlist, no links/`..`, size limits, sha256), `snapshot.py` (SQLite backup API), `formats/` (v1/v2 legacy + v3 → one `ImportModel`), `tasks/` (`export_game`, `import_game`, `backup` (+`backup_upload`), `restore`, `report`), `report/` (data + fpdf2 layout), `retention.py`, `scheduler.py`. Docker: `docker/Dockerfile.worker` (php-cli + python, runs as `www-data`).
- `conf/worker.php`: queue helpers for the website (`enqueueJob()`, `findJobForUser()`/`jobDownloadAllowed()`, `cancelJob()`, `workerActive()`), uploads (`storeArchiveUpload()`), backups in storage (`listBackups()`, pin/delete) and maintenance mode (`isMaintenance()`, `maintenanceResponse()`). `database.php` requires it.
- Runtime data (gitignored): `database/leaderboard.db` at repo root, assignment files in `htdocs/artifacts/`, game logos in `htdocs/uploads/`, and `storage/` (outside the web root: `incoming/` uploads, `jobs/<id>/` exports and reports, `backups/` with a `.json` beside each archive, `tmp/`, and `maintenance.json` during a restore).
- `IDEAS.md`: backlog. Design notes live in the READMEs (root, `agentic-service/`, `worker-service/`, `docker/`); keep them in sync with the code. Design and task files written while building a feature (`DESIGN.md`, `TASKS.md`, …) are temporary: when the feature is done, fold what still matters into the README, fix references to them, and delete them.

## Architecture
- **Auth**, four separate mechanisms:
  - Teachers: PHP session, managed by `conf/auth.php`. Every teacher page calls `requireTeacher($db)` or `requireAdmin($db)`; don't write your own login or role checks. They re-read the user from the DB on each request: deleted/deactivated/not-yet-activated users and a stale `session_version` are logged out (`login.php?expired=1`), `teacher_role`/`teacher_username` are refreshed, and `force_password_change` (and `REQUIRE_2FA_ADMIN`) blocks every page except `password.php` (`profile.php`), POSTs included. On `?ajax…` requests they return an empty 401/403 instead of redirecting. Bump `session_version` (`bumpSessionVersion()`) to log a user out everywhere.
  - Teacher accounts: admins invite by e-mail (`users.php` → `activate.php`); users can reset via `forgot_password.php` → `reset_password.php` and set up optional TOTP 2FA in `profile.php` (second login step: `login_2fa.php`). One-time links use `user_tokens` (`createUserToken()`/`findUserToken()`/`markTokenUsed()`; only the sha256 hash is stored, a new token of the same type invalidates older ones). Failed logins and reset requests are rate-limited via `login_attempts` (`isThrottled()`/`recordAttempt()`). Login always shows `LOGIN_ERROR`, whatever the cause.
  - Teams: no login. `team.php?token=<teams.access_token>`. Teams can sign themselves up via `join.php?code=<games.join_code>` when the game's registration is open.
  - Agents: `api.php`, `X-API-Token` header (or `?token=`), checked against `api_keys`. The agent sends only the header.
  - Worker: no HTTP at all. It works directly on the database and files; the website only enqueues `worker_jobs` rows and checks permissions.
  - Downloads: `job_download.php?id=` (task results, `jobDownloadAllowed()`, audit `JOB_DOWNLOAD`); `backups.php?download=` (admins). `team_download.php?token=<access_token>` (max 10 per level). `download.php?token=` from `download_tokens` only serves old links from the former level-up mail; no new tokens are made.
- **Teacher page pattern**: `session_start()` + requires (incl. `../conf/auth.php`, `../conf/game.php`) + `requireTeacher($db)`/`requireAdmin($db)` and, on game pages, `$game = requireGame($db, $user)`, then POST handlers (PRG: set `$_SESSION['success'|'error']`, e.g. via `flash()`, then redirect), then set `$pageTitle`/`$extraCSS`, then `include 'admin_header.php'` … `include 'admin_footer.php'`. Forms on user-management pages carry `csrfField()` and handlers check `verifyCsrf()`; do the same on new or changed pages (the older pages like `teacher.php` don't have CSRF yet).
- **Design** (`conf/theme.php`, principles in its header comment): one set of CSS tokens; light theme for the admin (follows `prefers-color-scheme`), dark `data-theme="ops"` for `index.php`, `beamer.php`, `team.php` and the auth/join pages (`authPageStart()`/`authPageEnd()`). Use the components instead of inline styles: `.btn` (`-primary`/`-secondary`/`-ghost`/`-success`/`-danger`, `-sm`, `-icon` with `aria-label`), `.badge`, `.card`/`.card-title`, `.stat`, `.table` in `.table-scroll`, `.field`, `alertBox()`, `<dialog class="modal">` (`data-open`/`data-close`), `progressBar()` (one segment per assignment), `rankBadge()`, `.bubble`, `.markdown[data-md]` (rendered by `renderMarkdown()`), `emptyState()`, `pageHeader()` (+ `gameSubtitle()`), `.menu` with `[data-menu]`, `[data-copy]`. Icons via `icon('name')` (Lucide paths), no emoji as icons. Status never by colour alone; animations respect `prefers-reduced-motion`.
- **Live updates** come from JS polling the same page with `?ajax...` params (e.g. `teacher.php?ajax_unread`, `messages.php?ajax=chat`). There are no websockets and no separate endpoints.
- **Games** (`conf/game.php`): `games.status` is `draft` → `running` ⇄ `paused` → `finished`; use `effective_status` from `getGame()` (or `effectiveStatusSql()`), which is `finished` once `ends_at` has passed. Admins control every game, teachers only the games linked in `game_teachers` (`canAccessGame()`). The active game is `$_SESSION['game_id']`, checked on every request by `requireGame()` (no access or no choice → `choose_game.php`, `?ajax…` → empty 403). Admins can delete a finished/draft game in the danger zone of `game.php` (`deleteGame()`: all rows of the game incl. archive and worker jobs, its attachments, uploaded logo and job results; backups stay; refused while running/paused or while a worker job for it is pending). When you add a table with `game_id`/`team_id`, also clean it up in `deleteGame()`, `resetGame()` and `deleteTeam()`. **Scope every query to the active game** and check any `team_id`/assignment `id` from POST/GET with `findTeamInGame()` (or `game_id = ?`).
- **Levels**: 0 = not started, 1..N = working on assignment N, N+1 = Finish (N = assignments in the game). `teams.current_level` == `assignments.assignment_number` within the same `game_id`. Ranking is `current_level DESC, level_updated_at ASC` within a game (`rankedTeams()`); progress is `(level − 1) / N` (`progressPercent()`). `startGame()` puts all level-0 teams on 1 with one shared time; `createTeam()` starts a team on `initialLevel()`.
- **Level-up/down**: always via `levelUp()`/`levelDown()` in `conf/game.php`. Level-up archives the chat (with `team_name`) to `completed_assignments` and deletes only that level's AI suggestions; `team_messages` stay, so a level-down brings the conversation back (and removes that level's archive row). No mail is sent.
- **Teams** see a waiting screen in `draft`, a banner in `paused` and an end screen in `finished`; `team.php` refuses team messages unless the game is running/paused. Times for the countdown (`seconds_left`) come from SQL, not the team's clock.
- **Announcements** (`announcements`, `team_id` NULL = all teams of the game) show up as a pop-up on `team.php`; the last closed id is kept in `localStorage`.
- `team_messages.sender` is one of `team`, `teacher`, `ai`, `suggestion`. `ai` = an AI message the team does see: `team.php` renders it exactly like `teacher` (teams can't tell), `messages.php` labels it "AI" with a robot icon, `levelUp()` archives it as `AI: …`. `suggestion` is teacher-only: filter `sender != 'suggestion'` anywhere teams or archives see messages. AI suggestions carry `ai_evaluation_id` (the row in `ai_evaluations`; `messages.php` renders intent/verdict/reason/proposed reply from it).
- **AI modes** (`teams.ai_mode`: `off` | `suggest` | `reply` | `auto`; set per team or for all teams in `teacher.php`, `games.ai_mode` is the default for new teams in `createTeam()`). `reply`/`auto` need an approved rubric (`assignments.ai_rubric_status = 'approved'`, edited as a table in `assignments.php`, never JSON for the teacher); `auto` falls back to `reply` when `ai_auto_allowed = 0`. Editing an approved assignment's `instruction`/`criteria` puts the rubric back to `draft` (`rubricStatusAfterEdit()`). The AI never changes `criteria`.
- **AI decisions** are proposed by the agent and re-checked by the server: `submitEvaluation()` stores every evaluation in `ai_evaluations`, applies `allowedDecision()` (only ever lowers: `paused`/no approved rubric/open escalation → suggestion) and marks results for an older message or level as `stale`. An escalation (`decision = 'escalate'`, `resolved_at` NULL) blocks the AI for that team: the team gets nothing until a teacher replies, the level changes, or an escalation button in `messages.php` is used (`resolveEscalations()`). Per team per level there is a progress record (`ai_team_progress`, quotes checked server-side) that teachers can clear in `messages.php`; it never reaches `team.php`. All AI actions are audited with `user_id` NULL (`AI_SUGGEST`, `AI_REPLY`, `AI_LEVEL_UP`, `AI_ESCALATE`). `ai_log.php` lists evaluations with the agents' output and reasoning, and the teacher's agree/disagree per assignment.
- **Worker tasks** (`worker_jobs`: `game_export`, `game_import`, `report`, `backup`, `backup_upload`, `restore`): pages call `enqueueJob()` (writes the audit row) and redirect to `jobs.php`, which polls `?ajax=jobs`. Teachers export and make reports for their own games (`game.php`); import (always a **new** game), backups and restores are admin-only (`games.php`, `backups.php`; restore needs the admin's password). Never put passwords or tokens in `params_json` (`enqueueJob()` refuses them). The worker logs `JOB_DONE`/`JOB_FAILED`, `GAME_IMPORT`, `BACKUP_RESTORE`, `BACKUP_DELETE` with `user_id` NULL.
- **Maintenance mode**: while the worker restores a backup, `storage/maintenance.json` exists and `getDB()` answers with a 503 (page that refreshes itself; empty for `?ajax…`; JSON for `api.php`, which the AI agent treats as "wait"). CLI scripts bypass it. A restore replaces the database, `htdocs/artifacts/` and `htdocs/uploads/`, makes a safety backup first, runs `bin/migrate.php`, and rolls back on failure.
- Every teacher-side mutation inserts an `audit_logs` row (`user_id`, `EVENT_TYPE`, description), via `logAudit()` in new code. Do the same for new actions. Never log passwords, tokens, TOTP secrets or codes.
- Team mail: only `sendTeamLinkEmail()` (dashboard link), sent by hand (📧, "send link" checkbox) or on self sign-up. Team names come from teams themselves, so mails go through `sendAccountEmail()`, which escapes everything.
- Mail functions no-op when `ENABLE_EMAIL` is `false` (use this for local testing). Admin-started invite/reset actions then show the link in the flash message; `forgot_password.php` only writes it to `error_log()`, never to the page. Mailpit runs alongside in Docker (see `docker/README.md`).

## AI agent protocol (`api.php?action=`)
`get_pending` (GET, `aiPendingTasks()`: teams of running/paused games with `ai_mode ≠ off` whose last team message has no teacher/ai/suggestion reply and no evaluation yet; per task the assignment, rubric, clarifications, recent attempt/question counts, `escalation_open`, progress and the level chat as `messages`) → `claim_task` → `submit_evaluation` (POST; the server re-checks and executes). Assignment assistant: `get_design_jobs` → `claim_design` → `submit_design` (`questions`, `rubric` or `error`; status `idle` → `pending` → `questions`/`draft`, max 3 question rounds). Plus `heartbeat` (with `model_ok`) / `unregister_agent`. Multiple agents can run at once. A claim locks the team (`teams.ai_processing_by/at`) or assignment (`assignments.ai_processing_by/at`) for 5 minutes; the same agent may renew it. The dashboard shows "active" when a heartbeat arrived in the last 120s, or "model niet bereikbaar" when every active agent reports `model_ok = 0`. Prompts get no team names, e-mails, tokens or teacher names; team text sits in delimited data blocks.

## Schema changes
There is no single schema file. `htdocs/setup.php` creates the base tables, and `bin/migrate.php` adds later columns/tables (idempotent: each `ALTER` is wrapped in try/catch). A fresh install needs **both**. When changing the schema, update the `CREATE TABLE` in `setup.php` **and** add an idempotent step to `migrate.php`.

- Game tables: `games` (`join_code` unique, `registration_open`, `logo_file`, `status_message`, `started_at`, `ends_at`), `game_teachers`, `announcements`; `game_id` on `teams`, `assignments`, `completed_assignments` (plus `team_name`), with unique indexes on `teams(game_id, team_name)` and `assignments(game_id, assignment_number)`. The migration puts existing data in the default game "Operation Gameplay".
- AI tables: `teams.ai_mode`; `games.ai_mode`, `ai_max_attempts`, `ai_max_questions` (1–50, per team per level per 10 min); `assignments.ai_rubric` (JSON), `ai_rubric_status` (`none`|`draft`|`approved`), `ai_design_status`, `ai_design_round`, `ai_auto_allowed`, `ai_processing_by/at`; `team_messages.ai_evaluation_id`; `ai_service_status.model_ok`; tables `ai_team_progress` (unique per team+level), `assignment_ai_dialog`, `ai_evaluations`. `deleteTeam()`/`resetGame()` remove the AI rows of those teams; `copyAssignments()` and the worker's game export/import carry `ai_rubric`, `ai_rubric_status` and `ai_auto_allowed` (not the dialog).
- Worker tables: `worker_jobs` (`type`, `game_id`, `params_json`, `status` `queued`|`running`|`done`|`failed`|`cancelled`, `progress`, `message`, `result_file` relative to `storage/`, `result_name`, `result_size`, `result_game_id`, `created_by`, timestamps, `expires_at`, `worker_id`) and `worker_status` (heartbeat; "active" within 120 s). `completed_assignments` also stores who approved and what: `leveled_by` (NULL = AI), `leveled_by_name`, `ai_evaluation_id`, `accepted_message_id`, `accepted_answer`, `level_started_at` (filled by `levelUp()`; NULL on rows from before, which the report derives from `chat_history` and `audit_logs`).
- User management tables: `teachers` (plus `email` with unique index `idx_teachers_email`, `display_name`, `created_at`, `last_login_at`, `session_version`, `totp_secret`/`totp_enabled`/`totp_last_step`; `username` and `password_hash` are `NULL` while an invite is pending), `user_tokens` (`invite` | `reset` | `email_change`), `user_recovery_codes`, `login_attempts`.
- SQLite refuses `ALTER TABLE … ADD COLUMN … DEFAULT CURRENT_TIMESTAMP` on a table with rows: add the column without a default, backfill with an `UPDATE`, and set the value explicitly on insert.
- `CURRENT_TIMESTAMP`/`datetime('now')` are UTC, while PHP's `date()` is local time. Do time arithmetic and comparisons in SQL (`expires_at > datetime('now')`), not in PHP; `formatDateTime()` converts for display.

## Running locally
Easiest: `docker compose -f docker/docker-compose.yml up -d --build`, then open http://localhost:8088/setup.php. Separate containers run the web app (`leaderboard`), the AI agent (`agent`, against the host's Ollama; it reads the `docker-agent` API key from the database volume read-only) and Mailpit; see `docker/README.md`. Manual setup:
```sh
git submodule update --init
cp conf/config.php.example conf/config.php   # then fill in SMTP and BASE_URL
(cd bin && ./setup.sh)                        # creates database/ + htdocs/artifacts/
php -S localhost:8000 -t htdocs               # open /setup.php → first admin account
php bin/migrate.php
(cd worker-service && python3 -m venv .venv && .venv/bin/pip install -r requirements.txt && .venv/bin/python main.py)
```

## Gotchas
- `BASE_URL` in `config.php` must be the public URL of `htdocs/` (no trailing slash): it's used for the links in download, invite, reset and e-mail confirmation mails.
- PHPMailer rejects a `FROM_EMAIL` without a TLD (e.g. `x@localhost`), even for Mailpit; use something like `leaderboard@example.com`.
- Older `config.php` files (from before the example was fixed) may still have the license comment above `<?php` and a `DB_FILE` that resolves to `conf/database/…`; the path should be `__DIR__ . '/../database/leaderboard.db'` to match `setup.sh` and the Python scripts (which hardcode that path).
- The root `.gitignore` (Python template) ignores `lib/`. The existing submodule still works, but adding a new one there needs `--force`.
- `DARKNET_CHAT_URL` in `config.php` (Docker: env `DARKNET_CHAT_URL`) shows the darknet chat under "Tools" in the admin sidebar; undefined or empty hides it.
- Never commit `conf/config.php` or any `config.py`: they hold SMTP credentials and API keys.
- The worker and the web server share the database, `htdocs/artifacts|uploads` and `storage/`: run them as the same user (Docker: `www-data`), and keep `STORAGE_DIR` in `conf/config.php` and `worker-service/config.py` the same. `RESULT_TTL_DAYS` and `MAX_ARCHIVE_MB` exist on both sides too.
- A backup contains password hashes, TOTP secrets, API keys and team tokens; it never contains `conf/config.php`. After restoring a backup with a different `docker-agent` key, restart the agent container.
- Archives are untrusted input: read them only through `worker/archive.py` (never `extractall`), and give imported files a name of our own.
- gpt-oss via Ollama cloud ignores `format` (JSON schema): `llm.py` therefore also puts the schema in the prompt, parses tolerantly and validates itself (one retry, then `LLMError` → escalation). The `-cloud` models need `ollama signin` on the Ollama host. Only cloud models are allowed (`CLOUD_ONLY` / `AI_CLOUD_ONLY`, default on; there is no GPU): local model names are refused at startup and by `LLMClient`.

## Conventions
- Code comments and most UI strings are Dutch. Match the surrounding file.
- Always use prepared statements, and escape output with `htmlspecialchars`.
- Stay framework-free: no Composer packages, bundlers, or shared CSS files unless asked.
